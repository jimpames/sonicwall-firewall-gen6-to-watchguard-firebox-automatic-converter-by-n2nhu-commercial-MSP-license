🎯 Captain — honest engineer-to-engineer answer. The reality is more nuanced than "just move the IP":
Part 1: Gateway (peer-addr) — YES, IP-form moves verbatim. Confirmed.
The toolkit calls ipaddress.ip_address(val) on the SW gateway primary <TOKEN> value:

If it parses as IP → emit IP verbatim in <peer-addr> AND make the backing address-group use that same IP as <host-ip-addr>. No operator action needed.
If it doesn't parse as IP → name-form path: emit name in <peer-addr>, backing group gets 0.0.0.0 placeholder, stderr warning printed. Operator edits placeholder.
Same code path for secondary gateways too. Your understanding is correct for the GW case.

Part 2: Tunnel (TUN) — partial. The honest read is this:
Look at what your golden master actually has (lines 20559-20560):

network local group "LAN Subnets"
network remote name someremotepeerfakeadrobj4Claude
Neither side gives a literal CIDR. The local side is a group reference ("LAN Subnets" — SonicWall's auto-generated group of all LAN subnets). The remote side is a name reference (someremotepeerfakeadrobj4Claude — which the user-address-object does define as host 14.14.14.14 in this config).

What "IPs in the config" actually means for TUN — three real cases:
Case A: SW has explicit network local network 10.5.0.0 255.255.0.0
The extractor vpn_local_network is wired up in sw_field_extractors.ini. Code at line 1757 captures it. BUT — and this is a real bug I just spotted — line 1763 reads local_cidr = parts[0] + '/24'. The toolkit hardcodes /24 regardless of the actual SW netmask. So 10.5.0.0/16 from SW would emit as 10.5.0.0/24 in WG. Operator must fix the prefix.

Case B: SW has explicit network remote host 14.14.14.14 (host form)
The extractor vpn_remote_host fires, line 1770 captures the IP into remote_ip, line 1775 emits <host-ip-addr>14.14.14.14</host-ip-addr>. Operator action: none. This case DOES work.

Case C: SW has network local group "LAN Subnets" OR network remote name someremotepeerfakeadrobj4Claude (group/name forms — what the golden master actually has)
Currently falls through to the placeholder fallbacks. Even though the underlying address-object someremotepeerfakeadrobj4Claude is defined as host 14.14.14.14 and the toolkit DOES resolve that name to 14.14.14.14 for the standalone alias (we shipped that in v1.8.3), the tunnel selector code doesn't reuse the same resolution. It's a missed integration.
